# 轮次边界契约

本文件在选择缺口、提交状态转换或自动续轮时读取。当前 Agent 使用相同的账本快照、状态转换和收尾对象；调用与展示可以由宿主编排，但不改变目标级循环责任。

## 开轮说明

先按[缺口推理说明](gap-reasoning.md)恢复事项目标、综合发现独立问题，并显式展示当前目录各不变量的适用对象、依据或未决问题。候选可来自任何证据，业务缺口应对应当前场景不变量责任；跨事项的延期清单不能替代事项内部问题比较。开轮说明需在实施前明确本轮问题、优先理由、完成证据和已知暂不解决的问题。

智能体从 `arckit-ledger-snapshot/v1.candidate_catalog` 恢复全部活跃事项与项目的已持久化候选，并记录本轮实际发现的新候选。用户可见的开轮说明和 `gap_selection.considered` 必须覆盖快照目录中的全部已持久化候选；每项写明资格、`selected`/`deferred`/`excluded`、优先级依据与理由，让任意候选 B 都能看出是否被考虑。恰好一项为 `selected`，`selected_ref` 与 `selected_gap.id` 一致。智能体可以自然转述已持久化候选的 `goal`/`reason`；这两个描述字段不是身份令牌，也不替代权威候选。

账本用事项级选择令牌强校验项目候选与选中事项候选，避免无关事项的并发提交使当前工作无效；其他事项的比较项作为同一快照下的审计证据，不扩大写入锁。若并发变化让新快照出现不同候选，下一轮必须重新比较，不能复用旧轨迹。

应用候选时，账本依据稳定 `selected_ref` 与缺口标识重新读取当前就绪候选，并把该权威对象写入轮次与收尾。选择令牌、项目修订号、事项 `updated_at`、候选身份或就绪性任一失配，仍须拒绝提交；只有智能体的语义等价改写不会触发过期失败。

比较是语义判断，不使用固定分数。智能体只声明它实际发现的新候选，不声称已经穷尽所有潜在工作。用户可见的开轮说明在执行工作前展示候选与选择理由；状态转换保存同一轨迹供账本验收和收尾回显。

## 缺口与本轮行动

已持久化缺口保存未成立的结果、未知、风险或验收边界，不保存未来执行步骤。`planned_transition` 是最新状态下只对本轮有效的行动。新增缺口即使成为唯一已持久化候选，也必须在下一快照中重新比较，不能由上一轮交接自动选中。

每轮从原任务和当前用户增量判断缺口的必要性。已持久化缺口、交接和不变量检查不提供新增授权；独立新问题只记录证据并提示。已偏离范围的旧缺口应通过正常取消接口注明理由，不继续执行以清空列表。

一个缺口表示当前尚未成立的具体结果，说明缺少什么、成立后改变什么以及足够证据；影响后续方向或多个对象、需要独立取舍的关键判断独立处理，工作量不直接决定粒度，紧密相关的低风险结果可共同验收，小任务可仅有一个普通缺口。选择理由应交代待回答的问题、独立解决的价值、完成证据和暂不解决的问题，使用 `goal`、`reason`、优先级依据、证据要求、选择轨迹和 `planned_transition.selection_assessment` 表达；先按可信场景定义检查局部前置，再比较优先级。

新事实按它与选中缺口的关系处理：

- 用于理解、解决或验证当前缺口：本轮继续使用，例如诊断中的新日志、复现条件、因果证据。
- 暴露另一个独立缺口：记录事实；原任务必需的工作形成候选，提交后重新读取最新状态并重新比较，不自动接续或顺带完成。
- 暴露原任务范围外的问题：记录提示，不作为当前任务必须清零的义务。

当前缺口已解决就提交，不因还有时间或同一智能体可以继续而包揽下一缺口。当前缺口未解决可以提交 `partial`，`resolution` 保持 `null`，下一循环可以继续同一个缺口。新知识出现、本轮结束和新建缺口是三件不同的事。

产品、交互、视觉、技术是事实视角，不是固定缺口分类。判断多个动作能否属于同一缺口，要问它们是否共同证明同一个结论，还是分别完成了可以独立讨论、取舍和验收的决定。同类事实中紧密相关且可共同决定的结果可以合并；建立预期与正式兑现实现不能合并。复用已接受预期不算重新建立。若仍有独立关键不确定性，先解决其中当前最重要的一项。

例如：用户待解决的故障或重要独立因果问题，直接原因未知时先定位原因，查清后重新比较处置；同一实现结果内的常规排障可继续，若动摇关键前提则保存证据后重选；交互语义未知时可能先确定行为，随后再判断是否需要技术验证；相关决策都已清楚时可直接选择实现缺口。顺序来自事实，不把这些例子变成固定路线图。

账本校验快照、候选、修订号、引用、状态转换结构和 `selection_assessment` 中明确声明的前置与合并冲突；上述因果边界由智能体正向遵守，不在运行时中复制判断机制或固定工作类型。

## 不变量判断

每个 v8 状态转换都携带当前项目修订版本下完整的 `invariant_assessment`。智能体从事项目标、相关预期、当前事实和未决问题判断责任，再结合动态使用的技能对每个项目不变量恰好判断一次。选择前显露义务，提交时更新判断；不以计划状态转换的预期动作或本轮实际编辑对象为适用性来源。具体状态、证据与反证语义由账本的 `references/invariant-assessment.md` 维护。

不变量的实际定义来自当前项目状态。逐项读取适用条件、应保持的状态和证据要求，不预设分类或数量。`not_relevant` 说明事实为何未触及该长期语义，`upheld` 给出与该不变量证据责任相符的持久证据，`threatened` 或 `undetermined` 引用已接受事实并绑定至少一个写回后仍开放的事项缺口。账本只校验完整覆盖、重复项、引用和处置结构，不判断语义相关性。

完整判断是对义务的识别，不是所有义务已经完成的声明。未选中的相关缺口可以保持 `threatened`/`undetermined` 并引用开放缺口；不要为清零不变量而补做独立工作，也不要把“本轮未选择”伪装成 `not_relevant`。多个不变量可以引用同一个真正解决共同问题的缺口，但不能用一个宽泛缺口吞并独立决定。

该判断是本轮事实视角，不是永久豁免。后续轮次每次重新覆盖全部目录；新事实可以把先前 `not_relevant` 或 `upheld` 改判为 `threatened`/`undetermined` 并重开结果型缺口。

## 收尾与最新状态读取

可信应用成功后返回 `arckit-round-closeout/v2`，内容来自实际提交后的权威状态：已接受增量、项目增量、`planned_transition`（含 `selection_assessment`）、不变量判断、证据、结果修订号、下一责任与提交后快照令牌。`next_candidate_projection` 固定为 `null`，写回候选不得用于续轮。

先展示收尾，再调用 `loop_snapshot read --after-commit <token>`。返回的快照必须标记 `observed_after_commit: true`；随后展示项目与事项修订号、观察时间与快照令牌，才可开始下一轮开轮说明。当前 Agent 负责调用并展示；宿主可以编排和透传同一回执，但不替代语义选择。

## 续轮门禁

人工确认目标后，当前 Agent 负责目标级循环。一次状态转换只接受一个有界 GAP 的主张；状态转换接受、`round_outcome: completed` 或账本收尾只表示这一轮事务结束，不表示 CASE、PROJECT 或原始用户目标完成。

每轮写回成功后必须先展示账本生成的收尾，再用提交后令牌读取并展示最新快照。Agent 以该快照和原始授权重新判断：

- 仍有授权范围内的就绪候选，或已有 GAP 在当前方法下可以继续推进：继续下一轮；
- 当前 GAP 需要更多同一验收内的证据：保留原 GAP，按 `partial` 继续；
- 新发现的独立必要结果：记录并在 fresh-read 后重新比较，不在本轮顺带解决；
- 局部需要人工决定或外部条件：保留阻塞，先推进其他独立且就绪的已授权工作；无其他可执行工作时才暂停并说明具体责任与恢复条件。用户停止或明确资源边界生效时立即停止，不因另有 GAP 而继续；
- 普通工作闭合：选择并完成 CASE 的完成复审；复审通过后再检查同一目标的其他 CASE 和剩余义务。

不按初始 GAP 列表顺序、写回成功、缺口数量、历史 `next_prompt` 或 `next_candidate_projection` 自动选择下一项。没有就绪候选也不能直接宣称目标完成，必须判断是完成复审、依赖阻塞、能力故障还是需要新的授权。

这里的“当前 Agent”不区分由宿主启动 session 还是由用户直接进入 session：技能加载后都由当前 Agent 承担上述语义循环。宿主可以提供上下文、执行工具和中断恢复，但不能替代提交后快照或从启动方式推断不同的 GAP 规则。

## 进展判断与执行交接

每次交接前，由同一智能体对照原任务、已确认授权、当前增量、已接受事实和最近执行证据，判断本轮改变了什么、还缺什么、下一步是否值得继续。历史进展声明是待复核的观察，不是已完成证明；轮数、文件数量、写回成功或缺口增减不能代替语义判断。

- 实际推进：说明消除的具体不确定性、障碍或新增的验收证据；部分推进可以保留同一个缺口。
- 必要准备：说明准备工作的必要性、已完成证据及其解除了哪项执行前置。恢复账本、建立事项或读取背景不自动等于业务结果改善，也不自动意味着应停止。前置已就绪且仍可在授权范围内推进时继续。
- 重复工作：对照历史说明为何同一问题仍未解决、是否获得了新证据。重复读取、重复造缺口或反复生成相同方案不能虚报推进；先选择有依据的不同方法。不存在可行的智能体下一步时，交代已尝试的方法与具体阻碍，再选择适当交接。

以上是判断角度，不是固定阶段或必须新增的状态枚举。宿主要求 `task_progress` 时，由智能体如实提交 `advanced`、`reason`、`evidence`、`remaining`；无论 `advanced` 为何，是否继续均由交接表达，不由该布尔值或固定阈值推导。缺失声明属于输出不完整，应在同一线程补齐，不能被解释成“无进展”。

交接使用现有责任契约：`agent` 表示有可执行的下一步，写明目标与依据；`human` 仅用于具体且必要的用户决定或输入，写明问题与阻塞关系；`external` 写明外部条件和恢复方式；`none` 表示结束执行并保留尚未完成的义务，不冒充事项已完成。智能体可以明确没有业务进展并继续必要准备；也可以在取得进展后按用户要求停止。

用户停止和显式资源边界始终有效。运行时可校验结构、权限、版本与提交合法性，处理进程故障和有界协议重试，并将观察交回同一线程；不得设置语义进展评分或以“连续无进展”覆盖智能体交接。旧记录中的阈值仅是历史数据。
