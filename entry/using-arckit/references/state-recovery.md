# 状态恢复与事项选择

每轮恢复上下文及选择或创建事项前读取。

## 方法与职责

本技能是通用状态驱动控制算法，不硬编码工作类型、产物类别或执行流程，也不规定技能、路径和工作顺序。场景语义来自可信 `snapshot.state_definition` 与项目状态；更换场景时替换状态定义及适配器，不改循环方法。事实变化通过事项影响记录和动态缺口推进。

用户原任务、当前增量与未撤回授权决定工作范围；状态、候选和后续发现不提供新增授权。依据可信的当前项目、事项状态判断，历史上下文、普通文件读取和写回返回值不能替代最新快照。每轮只推进一个可共同决策、共同验收的有界缺口；全面理解事实和识别义务，不等于本轮解决全部缺口。

不变量给出场景责任范围；候选来源不限，但业务缺口必须对应相关责任。控制、恢复与交接义务按其自身契约处理，不伪造业务映射。

当前智能体负责恢复全部相关信息、判断下一缺口的优先级、动态选择技能、工具和路径、完成工作并验证。智能体判断任务是否推进及是否继续，账本负责可信校验与写回，运行时执行交接与用户控制；智能体不直接手改账本，运行时不做语义预路由。

`using-arckit` 维护状态驱动方法；`arckit-development-ledger` 维护状态模型、提交接口与可信脚本。运行时通过各自能力清单分别调用，不在提示词或代码中重写本方法，也不从文件路径推断事实相关性。原有候选比较、因果边界和不变量判断全部适用。

宿主提供自动续轮、拒绝恢复或完成后的新发现时，读取[运行时与宿主边界](runtime-host-boundary.md)。该参考说明只解释执行上下文与方法的衔接，不替代正常循环。

## 恢复全部相关信息

事项（Case）是本次目标及其已知义务；缺口（Gap）是其中尚未成立的具体结果；循环（Loop）是围绕一个缺口取得证据、提交状态并重新选择的一轮。先理解结果，再填写协议。

**取得可信快照。** 每轮只接受账本能力产出的 `arckit-ledger-snapshot/v1`。运行时未提供时，智能体从已安装的 `arckit-development-ledger` 能力清单解析同一个 `loop_snapshot` 入口并自行调用；普通文件读取和写回返回值都不能冒充最新快照。

**检查可用性。** 最新权威状态不可用且账本兼容性探测报告协议不一致时，先进入协议恢复模式；此时不得创建、选择或推进普通事项缺口。恢复规则按需读取[协议兼容性恢复](protocol-compatibility-recovery.md)。`unavailable` 时暂停普通循环；协议恢复由同一智能体完成语义协调转换，可信账本原子验收成功后重新调用快照入口，再从原始用户事项判断。

**准备可写工作区。** 本轮将写入状态或证据时，遵循当前账本包的 `references/workspace-preparation.md`，通过其能力清单声明的入口完成工作区准备；宿主已提供本次准备回执时复用。准备失败先处理失败，不带病继续写入；纯只读分析不因恢复上下文而修改项目配置。回执中的既有 Git 跟踪问题应如实保留，不能把忽略规则生效当成历史跟踪已迁移。

**恢复事实源约定。** 项目根存在 `arckit/_kit/` 时，先读其 `README.md` 与 `CONVENTIONS.md`；未安装 definition 技能时，它是维护 `arckit/spec`、`arckit/tech`、`arckit/interaction`、`arckit/visual` 的模板与规范来源。项目自己的 `arckit/<domain>/CONVENTIONS.md` 和现有目录优先于 kit 默认结构。kit 只是项目内资源，不替代快照、技能判断或账本写回；模板默认值不是已确认事实。

**读取场景契约。** 读取 `snapshot.state_definition.definition` 的事实分类、选择规则、完成规则、实现判断指引和状态来源；首次使用该场景时，按定义指引读取随包概念示例。结合项目确认维护对象、实现载体、生效方式及验证方式，不按文件扩展名推断事实角色。稳定上下文在事项中保存一次，后续确认仍适用后引用；变化时更新，未知时说明缺口。定义缺失或不可用时先恢复可信能力。

**恢复状态与证据。** `available` 时读取用户当前增量、最新项目与迭代、全部活跃事项、场景定义、当前决策、不变量与候选目录，再读取完成判断所需的持久事实载体和工作区证据。

- 当前软件适配器的项目记录 `project-state-record/v5` 给出领域决策清单、当前决策、不变量和推进上下文。智能体必须逐项理解它们，但不会为每项制造过场缺口。
- 所有活跃事项使用 `development-case-record/v5`。事项只记录实际相关的事实、针对具体目标的影响、动态缺口、问题、交接和完成复审。

额外读取可以支持当前缺口的调查、实现与验证；新候选必须先通过原任务范围判断。正向轮次见[智能体循环对话协议](controller-conversation-protocol.md)，输入边界见[智能体循环输入边界](controller-input-boundary.md)。

## 事项选择与创建

结合用户意图、项目缺口、活跃事项、风险和依赖选择唯一事项。没有合适事项时返回 `case_control.create_case`：明确意图与结果、至少一个已接受事实（用户明确提出目标本身即可构成事实，不代表方案已经确定），以及由这些当前事实直接支持的初始缺口。已知未完成义务及真实依赖一并保留，不预测未知执行链。首个缺口依据关键阻塞与不确定性产生：可能是定位根因、明确产品行为、交互决策、技术验证，也可能直接实现；这些是例子，不是固定阶段或必经顺序。只有现有证据已经表明某个项目目标受到实际影响时才创建初始影响记录；允许为空，不预测影响范围。

注册后必须重新读取最新状态，不能预测账本生成的修订号或候选快照。
