# 提交、续轮与输出

提交状态转换及交接前读取。传输结构分别由[语义命令交接](semantic-command-handoff.md)和[收尾与交接](closeout-handoff.md)维护；候选比较、收尾展示及续轮边界由[轮次边界契约](round-boundary-contract.md)维护。

## 普通缺口提交

未完成验收时如实提交 `round_outcome: partial` 和已有证据，普通缺口的 `resolution` 为 `null`，保留原缺口；不得为满足校验而虚报完成或制造替代缺口。写回成功不等于原任务有进展：交接中说明实际消除的障碍或新增的验收证据，以及距原任务完成还缺什么。

声明完成前，按[缺口推理说明](gap-reasoning.md)将原缺口与历轮保留的义务对照本轮验收和证据；验收变化须说明原义务如何处置，不能只证明最新清单。义务未闭合则保留 `partial` 或按重新界定规则处理。完成复审同样复核这一对应关系，不以普通缺口已关闭替代判断。

## 选择提交接口

智能体不直接手改账本；只向可信入口提交事项控制、事项状态转换或交接。

- 当前上下文提供 `arckit-semantic-case-command/v1` 输出契约时，读取[语义命令交接](semantic-command-handoff.md)，提交绑定快照的语义命令：Agent 显式声明候选比较、事实、缺口、影响、项目决策与不变量判断及其关系，使用带类型的稳定引用与命令内局部句柄，不生成权威标识或修订号、选中缺口副本、反向索引或内部状态转换。可信账本独占确定性物化和原子提交。
- 当前上下文未提供该输出契约时，按[收尾与交接](closeout-handoff.md)使用权威 `arckit-case-transition/v8` 入口。两者只决定提交格式，不决定当前 Agent 是否继续目标级循环。

两种传输方式都只承载同一个智能体语义主张；软件定义决策在被真正澄清的当轮就进入项目状态。

## 复审提交

完成复审候选只由复审结果或独立的人工预算授权完成，不使用普通缺口的 `resolution`，也不携带事项内容变化；发现的问题由账本派生为下一轮普通修复缺口。

## 自动续轮

每次交接前读取[轮次边界契约](round-boundary-contract.md#进展判断与执行交接)的“进展判断与执行交接”，结合原任务、已确认授权、当前证据和历史观察判断实际推进、必要准备或重复工作，明确下一责任与理由。进展判断属于当前 Agent；运行时不按轮数、写回、缺口变化或缺失字段替代判断。

状态转换接受后只结束本轮账本事务，不结束目标执行。未验收完成时保留选中缺口，不为续轮另造缺口；展示收尾并重读可信快照后，按[续轮门禁](round-boundary-contract.md#续轮门禁)重新判断原任务范围与当前优先级。只要授权有效且仍有可执行工作，当前 Agent 继续下一轮工具调用，不用最终答复等待用户说“继续”。

账本写回成功后，先向用户展示其 `arckit-round-closeout/v2`：实际接受的事实、影响、缺口、项目变更、完整不变量判断、结果修订号和证据；该回执不包含下一候选。随后用回执的提交后令牌单独调用 `loop_snapshot`，展示最新状态读取回执后才可独立判断下一缺口。运行时也必须按同一顺序透传这两个回执，不重新组装语义。其余续轮和停止规则见[轮次边界契约](round-boundary-contract.md)。

## 输出

- 协议不一致时：可信协调转换结果、保真声明、剩余不确定性和最新状态读取交接
- 选中事项和动态缺口，或完整 `case_control.create_case`
- 本轮 `selection_assessment`、决策、事实、不变量、技能、工具与证据摘要
- 绑定宿主的 `arckit-semantic-case-command/v1`、直接提交的 `arckit-case-transition/v8`，或明确交接
- 用户可见的开轮说明、已接受的轮次收尾与写后最新状态读取回执
- `round_outcome`、`case_resolution`、`project_state_delta`、`loop-handoff/v2`
- 原任务进展、依据、剩余义务与执行交接；宿主要求时按 `task_progress` 和 `handoff` 契约提交
