# 使用 Arckit

本技能是通用状态驱动控制算法，不硬编码工作类型、产物类别或执行流程，也不规定技能、路径和工作顺序。场景语义来自可信 `snapshot.state_definition` 与项目状态；更换场景时替换状态定义及适配器，不改循环方法。事实变化通过事项影响记录和动态缺口推进。

## 全程约束

- **范围**：用户原任务、当前增量与未撤回授权决定工作范围；状态、候选和后续发现不提供新增授权。
- **事实**：依据可信的当前项目、事项状态判断，历史上下文、普通文件读取和写回返回值不能替代最新快照。
- **聚焦**：每轮只推进一个可共同决策、共同验收的有界缺口；全面理解事实和识别义务，不等于本轮解决全部缺口。
- **保障**：不变量给出场景责任范围；候选来源不限，但业务缺口必须对应相关责任。控制、恢复与交接义务按其自身契约处理，不伪造业务映射。
- **职责**：智能体判断任务是否推进及是否继续，账本负责可信校验与写回，运行时执行交接与用户控制；智能体不直接手改账本。

## 职责与宿主接入

当前智能体负责恢复全部相关信息、判断下一缺口的优先级、动态选择技能、工具和路径、完成工作并验证。运行时不做语义预路由。

本入口维护状态驱动方法；`arckit-development-ledger` 维护状态模型、提交接口与可信脚本。运行时通过各自能力清单分别调用，不在提示词或代码中重写本方法，也不从文件路径推断事实相关性。原有候选比较、因果边界和不变量判断全部适用。

宿主提供自动续轮、拒绝恢复或完成后的新发现时，读取[运行时与宿主边界](references/runtime-host-boundary.md)。该参考说明只解释执行上下文与方法的衔接，不替代正常循环。

## 状态驱动循环

### 1. 恢复全部相关信息

事项（Case）是本次目标及其已知义务；缺口（Gap）是其中尚未成立的具体结果；循环（Loop）是围绕一个缺口取得证据、提交状态并重新选择的一轮。先理解结果，再填写协议。

**取得可信快照。** 每轮只接受账本能力产出的 `arckit-ledger-snapshot/v1`。运行时未提供时，智能体从已安装的 `arckit-development-ledger` 能力清单解析同一个 `loop_snapshot` 入口并自行调用；普通文件读取和写回返回值都不能冒充最新快照。

**检查可用性。** 最新权威状态不可用且账本兼容性探测报告协议不一致时，先进入协议恢复模式；此时不得创建、选择或推进普通事项缺口。恢复规则按需读取[协议兼容性恢复](references/protocol-compatibility-recovery.md)。`unavailable` 时暂停普通循环；协议恢复由同一智能体完成语义协调转换，可信账本原子验收成功后重新调用快照入口，再从原始用户事项判断。

**准备可写工作区。** 本轮将写入状态或证据时，遵循当前账本包的 `references/workspace-preparation.md`，通过其能力清单声明的入口完成工作区准备；宿主已提供本次准备回执时复用。准备失败先处理失败，不带病继续写入；纯只读分析不因恢复上下文而修改项目配置。回执中的既有 Git 跟踪问题应如实保留，不能把忽略规则生效当成历史跟踪已迁移。

**读取场景契约。** 读取 `snapshot.state_definition.definition` 的事实分类、选择规则、完成规则、实现判断指引和状态来源；首次使用该场景时，按定义指引读取随包概念示例。结合项目确认维护对象、实现载体、生效方式及验证方式，不按文件扩展名推断事实角色。稳定上下文在事项中保存一次，后续确认仍适用后引用；变化时更新，未知时说明缺口。定义缺失或不可用时先恢复可信能力。

**恢复状态与证据。** `available` 时读取用户当前增量、最新项目与迭代、全部活跃事项、场景定义、当前决策、不变量与候选目录，再读取完成判断所需的持久事实载体和工作区证据。

- 当前软件适配器的项目记录 `project-state-record/v5` 给出领域决策清单、当前决策、不变量和推进上下文。智能体必须逐项理解它们，但不会为每项制造过场缺口。
- 所有活跃事项使用 `development-case-record/v5`。事项只记录实际相关的事实、针对具体目标的影响、动态缺口、问题、交接和完成复审。

额外读取可以支持当前缺口的调查、实现与验证；新候选必须先通过原任务范围判断。正向轮次见[智能体循环对话协议](references/controller-conversation-protocol.md)，输入边界见[智能体循环输入边界](references/controller-input-boundary.md)。

### 2. 选择或创建事项

结合用户意图、项目缺口、活跃事项、风险和依赖选择唯一事项。没有合适事项时返回 `case_control.create_case`：明确意图与结果、至少一个已接受事实（用户明确提出目标本身即可构成事实，不代表方案已经确定），以及由这些当前事实直接支持的初始缺口。已知未完成义务及真实依赖一并保留，不预测未知执行链。首个缺口依据关键阻塞与不确定性产生：可能是定位根因、明确产品行为、交互决策、技术验证，也可能直接实现；这些是例子，不是固定阶段或必经顺序。只有现有证据已经表明某个项目目标受到实际影响时才创建初始影响记录；允许为空，不预测影响范围。

### 3. 动态选择下一缺口

**识别相关义务。** 选择缺口前读取[事项目标、缺口与必需保障](references/gap-reasoning.md)，从原任务、用户增量、相关预期、当前事实、执行反馈、依赖与外部条件综合发现问题。同时逐项读取当前项目不变量目录的 `applies_when`、`must_hold`、`evidence_expectation` 与 `priority`，理解后显式说明各项在本事项的适用对象、依据和未决问题，作为选题依据之一。适用性包括尚未调查的必要预期与缺失，不从计划状态转换或准备修改哪些内容倒推。维度的数量、内容和证据责任完全来自动态读取的定义；`required` 表示必须考虑，不表示本轮清零或固定排序。

不变量不规定工作类型、技能、路径或执行顺序，也不等于必须更新某个载体。实际相关的长期判断不能静默遗漏：已有事实充分时显式确认，事实域无关时说明依据，相关但未解决时如实标记并由开放缺口承接，不为了让所有判断变成 `upheld` 而补做独立决策。

只有原任务验收必需、确实阻塞原任务或修复本次修改引入的回归时，缺失、过时、含糊、冲突或证据不足的结果才形成当前事项的开放缺口；独立问题作为提示，不因不变量检查扩大任务。既有结论不会永久豁免，后续事实可以重新威胁它并产生新缺口。

只有当前状态转换会对项目目标形成可接受结论时才记录影响。对实际相关目标的判断为：

- 已满足：`upheld` + 持久证据。
- 被威胁：`threatened` + 开放缺口。
- 证据不足：`undetermined` + 调查或澄清缺口。
- 不相关：不创建影响记录；但在本轮 `invariant_assessment` 中记录 `not_relevant` 理由。

**先判断当前能否推进。** 按场景规则检查局部事实与共享依赖。问：剩余未知的不同答案，是否会改变本次结果、关键约束或验收标准？若会改变重要决定，先选择能区分答案的取证问题；若不影响本范围，说明依据并保留未知。前置未满足的候选先处理前置或交接，优先级不能绕过资格。将选择依据写入 `planned_transition.selection_assessment`，字段语义见[缺口选择说明](references/selection-assessment.md)。它区分探索与正式建立，并明确本轮验收及未决义务。

正式确立结论前，按[缺口推理说明](references/gap-reasoning.md)核对其中每项重要决定的来源、成立条件和未决依赖；目标明确不能替代智能体补充决定所需的依据。合并前检查内部依赖，不能把尚待取证的问题和依赖其答案的重要决定一起认定为可正式确立。

**明确这一轮要成立什么。** 缺口表达尚未成立的具体结果，说明缺什么、成立后改变什么、何种证据足够。子结果共享目标、前提和验收边界时可以合并；若答案会改变后续方向、影响多个对象或需要独立取舍，则在这个判断处收紧边界。工作量、文件或测试数量不直接决定缺口数；大工作可以 `partial` 跨轮，小任务可只有一个普通缺口。遵守场景中的事实顺序与合并禁区。

**比较候选并展示选择。** 根据本轮快照比较账本为全部活跃事项与项目派生的已持久化候选，以及当前上下文刚显露的新发现候选，在合格候选中选择最能解除当前目标关键阻塞、减少重大返工或产生直接价值的结果。影响面、不确定性、风险与依赖用于解释判断，不按陌生程度排序。选择前向用户展示独立的开轮说明：列出全部已持久化候选、实际发现的新候选、`selected`/`deferred`/`excluded` 与简短理由；不得声称穷尽了尚未发现的新工作。完整比较轨迹随状态转换保存，其中项目与选中事项范围由事项级选择令牌强绑定，以保留无关事项的并发推进。细则见[轮次边界契约](references/round-boundary-contract.md)。

**普通工作闭合后选择复审。** 完成复审（Completion Review）是唯一显式语义自查，只在授权范围内的普通工作闭合后检查结果正确性、问题是否真实解决、验证可信度、回归风险与最小性。普通缺口的证据收集和确定性校验不是额外复审阶段。

### 4. 同一智能体完成一个缺口

**工作到当前结果成立或需要重新决定。** 围绕选中缺口的结果动态使用必要技能和工具。调查、比较、试验可用于证明当前结果；证据足够时验收，未足够则保留 `partial`。若需要另行选择的独立结果或重要决定首次具备条件，或新证据使已接受预期、关键前提、责任或验收边界需要重定，保存当前证据及义务，提交并重新读取最新状态后重选。同一验收内的动作依赖就绪、约束内的方法调整与常规排障可继续；独立因果问题按场景规则处理。不因探索标签自动换缺口，也不以实验存在宣称正式兑现；关键前置缺失仍先取得依据。

专业技能是独立可复用能力，不是不变量的一一对应执行模块。智能体依据当前目标选择并读取其方法，在授权与选中缺口边界内使用；专业技能包含的后续流程不自动扩大本轮目标。若其必要步骤与当前边界冲突，显式报告冲突和剩余义务，不能静默越界或跳过方法门禁。

**处理新事实。** 新事实用于理解、解决或验证当前选中的缺口时，可以在本轮继续使用；暴露另一个独立缺口时，只记录事实与必要候选，不顺带解决。当前缺口解决后提交并重新读取最新状态，再独立选择下一缺口；需要用户决定时交接人工。

新证据涉及已有主张时，按[缺口推理说明](references/gap-reasoning.md)核对具体主张及其条件，区分用户目标与智能体补充的决定。说明哪些仍成立、哪些需调整、哪些尚未知，并重审依赖它们的缺口资格；“目标没变”不能替代这项核对。

若新事实证明既有缺口过宽或前提失效，按[缺口推理说明](references/gap-reasoning.md)的重新界定规则保留未完成义务，通过可信接口记录取消或替代后重新读取最新状态并重选；不把取消宣称为完成，不为续轮换号。

**维护已建立的结论。** 全面理解相关事实与判断不变量，不等于本轮补齐全部预期事实。只建立解决选中缺口所需的新结论；同一有界结论集合可以同步多个事实载体；相关低风险结论可以共同建立，独立重要决策与场景规定不可合并的结论必须分开。

**结果验证前确定证据上下文。** 检查结果是否符合明确预期时，在运行会产生验证文件的工具或脚本前，读取 `arckit-development-ledger` 的 `references/case-evidence.md`，明确待验证主张、已确认的事项身份、本次运行输出目录及保留方式，并将其作为当前执行上下文供所选技能和工具使用。区分交付物、可复用验证源码与本次运行证据；路径不决定事实角色。当前软件适配器的证据根为 `arckit/cases/evidence/<case-id>/`，具体组织、读取核验、引用和清理由该约定承载。已有事实载体直接引用，不新增重复报告；结果验证工具的默认输出位置与当前上下文冲突时先调整输出配置，不能等产物散落后再决定归档。此上下文由同一智能体维护，不新增运行时路由或状态协议。

结论形成或改变的当轮维护对应事实载体，优先更新已有文档。新反证须重审全部实际相关判断，明确哪些旧主张失效或仍有依据；不以文件存在、测试数量或某一问题已修复支持其他未决主张。

### 5. 提交状态转换

**普通缺口提交。** 未完成验收时如实提交 `round_outcome: partial` 和已有证据，普通缺口的 `resolution` 为 `null`，保留原缺口；不得为满足校验而虚报完成或制造替代缺口。写回成功不等于原任务有进展：交接中说明实际消除的障碍或新增的验收证据，以及距原任务完成还缺什么。

声明完成前，按[缺口推理说明](references/gap-reasoning.md)将原缺口与历轮保留的义务对照本轮验收和证据；验收变化须说明原义务如何处置，不能只证明最新清单。义务未闭合则保留 `partial` 或按重新界定规则处理。完成复审同样复核这一对应关系，不以普通缺口已关闭替代判断。

**选择提交接口。** 智能体不直接手改账本；只向可信入口提交事项控制、事项状态转换或交接。

- 宿主声明 `arckit-semantic-case-command/v1` 输出时，读取[语义命令交接](references/semantic-command-handoff.md)，提交绑定快照的语义命令：智能体显式声明候选比较、事实、缺口、影响、项目决策与不变量判断及其关系，使用带类型的稳定引用与命令内局部句柄，不生成权威标识或修订号、选中缺口副本、反向索引或内部状态转换。可信账本独占确定性物化和原子提交。
- 直接调用的智能体未获得该输出契约时，按[收尾与交接](references/closeout-handoff.md)使用权威 `arckit-case-transition/v8` 入口。

两种传输方式都只承载同一个智能体语义主张；软件定义决策在被真正澄清的当轮就进入项目状态。

**复审提交。** 完成复审候选只由复审结果或独立的人工预算授权完成，不使用普通缺口的 `resolution`，也不携带事项内容变化；发现的问题由账本派生为下一轮普通修复缺口。

### 6. 自动续轮

每次交接前读取[轮次边界契约](references/round-boundary-contract.md#进展判断与执行交接)的“进展判断与执行交接”，结合原任务、当前证据和历史观察判断实际推进、必要准备或重复工作，明确下一责任与理由。进展判断属于智能体；运行时不按轮数、写回、缺口变化或缺失字段替代判断。

状态转换接受后结束本轮。未验收完成时保留选中缺口，不为续轮另造缺口；后续选择仍须重新判断原任务范围与当前优先级。

账本写回成功后，先向用户展示其 `arckit-round-closeout/v2`：实际接受的事实、影响、缺口、项目变更、完整不变量判断、结果修订号和证据；该回执不包含下一候选。随后用回执的提交后令牌单独调用 `loop_snapshot`，展示最新状态读取回执后才可独立判断下一缺口。运行时也必须按同一顺序透传这两个回执，不重新组装语义。其余续轮和停止规则见[轮次边界契约](references/round-boundary-contract.md)。

## 输出

- 协议不一致时：可信协调转换结果、保真声明、剩余不确定性和最新状态读取交接
- 选中事项和动态缺口，或完整 `case_control.create_case`
- 本轮 `selection_assessment`、决策、事实、不变量、技能、工具与证据摘要
- 绑定宿主的 `arckit-semantic-case-command/v1`、直接提交的 `arckit-case-transition/v8`，或明确交接
- 用户可见的开轮说明、已接受的轮次收尾与写后最新状态读取回执
- `round_outcome`、`case_resolution`、`project_state_delta`、`loop-handoff/v2`
- 原任务进展、依据、剩余义务与执行交接；宿主要求时按 `task_progress` 和 `handoff` 契约提交
