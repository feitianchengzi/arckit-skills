# 事项完成复审

完成复审是普通动态缺口、问题、交接和 `threatened`/`undetermined` 影响全部闭合后的事项终态门禁，也是唯一显式语义自查。它不是软件事实、项目决策或不变量，也不是普通分面，不承担常规产品、交互、视觉、技术、代码或验证补齐；普通缺口的证据收集和账本校验不构成额外复审。

账本只在普通工作闭合且最新内容轮次已对当前项目不变量目录完成有效判断后派生复审候选；同一智能体若从最新状态发现更重要的普通工作，可用 `fresh` 选择先完成它。只有不存在此类工作时才执行语义审查。复审状态转换自身也提交最新不变量判断；发现的问题先转成普通动态缺口，后续轮次再处理，不能在复审当轮顺带修复。只有后续调查确认的稳定结论才可能通过普通状态转换成为事实。`clean` 复审关闭事项后，运行时只可执行仅涉及 Git 的收尾。

复审范围由事项授权目标限定：探索任务检查证据与未知是否回答，定义任务检查预期是否成立；不要求补做未授权的产品实现。实现载体依项目而定，技能、配置等同样可以是实现。

## 五个维度

- `implementation_correctness`：实现符合相关已接受事实、软件决策与判断为 `upheld` 的不变量。
- `problem_resolution`：原始问题或目标真实闭合。
- `verification_credibility`：验证覆盖主要风险并可重复。
- `regression_risk`：没有未处理的回归与边界破坏。
- `minimality`：没有无必要修改或过度设计。

复审必须绑定当前 `content_revision` 并提供证据。`clean` 不能带问题，也不能与内容变更同轮提交。

复审问题类型为 `error | omission | excess`，并转换为普通动态缺口。修复或有证据的处置提升内容修订号，使旧复审失效；随后重新审查。复审可以意外发现定义或设计遗漏，但这只是查缺补漏，不是日常文档推进机制。

自主 `cycle_count` 只统计 `reviewer=agent`；上限是策略快照加人工授权扩展。最后一个授权轮次仍非 `clean` 时进入仅由人工负责的缺口。只有当前 `human` 责任可提交人工 `clean` 复审、风险处置或带证据的有限预算扩展；既有计数不清零。
