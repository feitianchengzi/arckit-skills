# 平台通用 Git 触发约定

本引用文档定义平台无关的分支、标签和远端工作流触发契约。它不描述构建、上传、审核、账号、签名或外部平台配置步骤。

## 操作授权

操作级授权及其有效期以 [SKILL.md 的入口授权门禁](../SKILL.md#入口授权门禁) 为准。下列示例用于应用该门禁，不新增授权。

代表性判断：

- “git commit”“提交这些改动”“把改动提交一下” -> 只授权在当前分支暂存/提交，不授权分支变更或推送。
- 当前 `main` + “git commit” -> 保持 `main` 并提交。
- 当前 `feature/a` + “git commit” -> 保持 `feature/a` 并提交。
- “创建 feature/a 后提交” -> 检查状态并按明确授权创建/切换后提交。
- “按分支规范准备发布” -> 先推荐发布分支/标签基线，不执行分支或标签写操作。
- 已明确授权某标签与基线的创建/推送，随后仅补充版本说明 -> 原授权仍有效且目标未变时继续执行，不重复确认。
- 只要求创建标签 -> 不因这项授权自行创建、切换或推送分支。

## 核心模型

- 分支决定代码生命周期。
- 标签标识版本，远端工作流按约定识别出包意图。
- 标签不强制绑定 `release/*`。
- 已存在的 `release/*` 是版本稳定线；同一发布单元的版本基线按下方“基线策略”核对，不能绕过对应稳定线。
- 默认推荐通过标签推送触发出包，不推荐为渠道创建分支；已有 CI 的实际触发方式以“工作流触发模式”为准，不自动改造。

## 分支策略

`main`

- 唯一长期开发主线。
- 日常迭代、新功能、小修复默认进入 `main`。

`feature/<topic>`

- 可选隔离分支。
- 仅用于长周期、高风险、多人协作、实验性开发或需要独立评审的工作。
- 上述条件只支持推荐，不授权自动创建；必须由用户明确要求或确认。
- 完成后合回 `main`，不直接合入 `release/*`。

`release/vx.x.x`

- 版本稳定线，从 `main` 在准备发布某个版本时拆出。
- 创建后版本范围冻结，只接收该版本发布所需的缺陷修复、配置修正、文案修正和兼容性修复。
- 不接收新功能、无关重构或实验代码。

`hotfix/<topic>`

- 可选紧急修复分支。
- 如果对应 `release/*` 仍活跃，优先直接在 `release/*` 上修复。
- 只有发布分支已归档、删除，或需要从正式发布标签拉出干净修复线时使用。

## 合并策略

- `feature/* -> main`
- `main -> release/vx.x.x` 只用于首次创建发布分支。
- `release/*` 创建后，不再整体合并 `main`。
- `main --cherry-pick/backport--> release/vx.x.x` 只用于明确属于该版本的必要修复。
- `release/vx.x.x -> main` 用于发布分支修复回流。
- `hotfix/* -> main`，并按需同步到活跃 `release/*`。
- 多个 `release/*` 活跃时，每个发布/紧急修复分支的修复都要评估是否同步到其他发布线。

## 标签策略

标签命名：

- `vx.x.x-alpha.N`：早期预发布，例如 `v1.2.3-alpha.1`。
- `vx.x.x-beta.N`：`beta` 测试版本，例如 `v1.2.3-beta.1`。
- `vx.x.x-rc.N`：正式发布候选，例如 `v1.2.3-rc.1`。
- `vx.x.x`：正式版本，例如 `v1.2.3`；标签不代表部署或平台发布已成功。
- 默认采用 SemVer 版本部分，`v` 是 Git 标签前缀。已有版本/标签约定优先，不自动重命名历史标签或修改 CI。
- 独立发布单元可采用 `<unit>/v<version>`；已有命名空间及包管理生态要求优先。同一产品的不同平台构建不必分别命名。
- 标签表达版本；构建号和分发渠道由项目构建/发布配置管理，不编码为平台渠道前缀。

请求映射：

- 明确 `alpha`、`beta`、发布候选或正式版本时，使用对应阶段的标签；无需依次经历全部阶段。
- 内测、公测、测试分发或环境名称只表达分发意图，不能单独决定 `alpha`/`beta`/`rc`；结合项目版本事实推荐，信息不足时说明待确定阶段。
- “正式发布候选”使用 `-rc.N`，“正式版本”使用无预发布后缀的标签。

`N` 在同一发布单元、目标版本和预发布阶段内从 1 开始递增，使用独立数字段（如 `rc.2`、`rc.10`），按 SemVer 规则排序。结合下方“Git 检查”中的标签历史检查选择序号；历史不可见时不能把 `.1` 当成已确认可用的序号。

版本命名与排序依据：[Semantic Versioning 2.0.0](https://semver.org/)。

## 基线策略

- 先根据仓库版本声明、历史标签和发布配置确定发布单元及维护线归属；版本比较、标签历史和维护线检查仅在同一发布单元内进行。归属不明时报告缺口，不拿其他单元的高版本约束当前发布，也不自动引入新的分支命名体系。
- 标签阶段由版本成熟度决定，下列基线偏好由发布用途决定；两者分别判断。
- 内部测试标签可以基于 `main` 或 `release/*`。
- 外部测试或公测标签默认应基于 `release/*`；如果用户明确要从 `main` 出外部测试，先说明风险并等待确认。
- 正式发布候选或正式版本标签必须基于 `release/*`、正式发布修复线，或用户明确确认的发布候选提交；不要默认从 `main` 直接创建。
- 如果 `release/vx.x.x` 已存在，该版本的预发布和正式标签默认都应基于该发布线。
- 如果已有更高版本 `release/*`，不要从 `main` 给更低版本直接打标签；先确认对应发布/紧急修复基线。
- 如果目标版本没有 `release/*`，内部测试可以基于 `main`，不要强迫创建发布分支。
- 如果目标版本没有 `release/*`，外部测试或正式候选应建议先创建 `release/vx.x.x`，但必须由用户确认。

## 工作流触发模式

先只读核对仓库内 CI 的触发事件、引用过滤及手动输入。已有配置决定实际触发行为，下面仅是无既有约定时的推荐模式；不以建议覆盖项目事实。

远端工作流推荐监听：

- `release/v*` 分支推送：版本线验证。
- `v*` 标签推送：版本出包入口；使用命名空间时采用对应 `<unit>/v*`。
- 工作流应校验完整标签，再区分 `-alpha.N`、`-beta.N`、`-rc.N` 和正式版本；`v*` 本身不能区分阶段。
- 版本阶段与构建目标、环境或分发渠道的映射以项目配置为准，不预设平台专用监听规则。
- 已有流程采用手动输入既有标签时，报告对应输入和配置位置；推送该标签不等于启动流水线，Git 授权不包含手动启动。
- 建议命名与现有监听条件不匹配时，报告差异与预期影响，不自动改 CI，也不声称标签推送必然出包。

智能体只负责推荐、创建和推送分支/标签。推送后不继续追踪远端工作流、构建产物、上传状态或发布平台状态。

如果仓库中找不到 fastlane、CI、远端工作流或平台发布配置，只能报告“远端监听不可见”或请求用户确认监听规则。配置不可见不构成回退到本机的理由；不要改走本机构建、归档、导出、上传、签名或发布平台操作。

## Git 检查

推荐或执行前允许读取 Git 状态/历史及仓库内版本、发布说明和 CI 配置；文件读取不构成构建或平台操作授权。Git 只读命令例如 `git status`、`git branch`、`git tag`、`git ls-remote`、`git log`、`git rev-parse`、`git show`、`git merge-base`。

必须检查：

- 当前分支和工作区状态，用于判断操作环境；不以当前 `HEAD` 代替用户指定的发布目标。
- 目标远端、本地和远端是否存在同一发布单元的目标 `release/vx.x.x` 或项目已明确映射的维护线。
- 同一发布单元是否存在更高版本活跃 `release/*`。
- 本地和远端是否已存在目标标签，以及选择预发布序号所需的同版本同阶段标签历史；远端不可访问时报告未知。
- 将目标基线或用户指定的提交解析为目标提交 SHA，检查其是否符合“基线策略”；使用分支基线时核对目标提交的包含关系，使用明确确认的候选提交例外时记录依据。
- 核对目标提交中的版本声明和相关 CI 配置；读取当前工作区文件时，标明与目标提交的差异，不能把未提交配置当作已生效的远端规则。
- 标签应指向上述目标提交；当前分支可以不同，创建标签本身不要求切换分支。

## 失败证据

远端工作流失败但没有具体错误时，先让用户收集失败原因，不要进入本地构建、上传或猜测修复。

优先收集：

- 触发分支或标签。
- 提交哈希。
- 工作流名称、运行时间和失败阶段。
- 工作流界面中的失败标题和具体错误。
- 平台发送到开发者、维护者或发布负责人的通知邮件原文。
- 如果平台界面的日志/产物显示成功但总状态失败，继续查平台级发布、上传或处理阶段的失败通知。

拿到具体失败原因前，只输出“去哪里找错误”和“需要粘贴哪些信息”，不能给出修复方案。
