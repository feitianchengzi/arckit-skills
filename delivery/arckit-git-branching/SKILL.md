# Arckit Git 分支管理

把发布相关请求收敛到 Git 层：分支决定代码生命周期，标签标识版本，远端工作流按约定识别出包意图。标签不强制绑定 `release/*`，但必须尊重已存在的版本稳定线。

## 使用边界

- 默认保持命令执行前的当前分支；不得根据任务规模、风险、发布规范或先前策略讨论自行创建或切换分支。
- 用户只要求 `status`、`add`、`commit`、`log`、`diff` 或其他非分支操作时，只授权该操作；`git commit` 必须提交到当前分支，不授权创建、切换、合并或删除分支。
- 创建、切换、合并、删除、回流或推送分支必须来自用户对该操作和目标分支的显式要求或确认；一种 Git 写操作的授权不能传递为另一种操作的授权。
- 发布分支/标签/出包规则只约束用户明确选择的发布分支或标签操作，不自动改变普通提交所在分支，也不把“推荐功能/发布分支”变成执行授权。
- 只处理 `main`、`feature/*`、`release/*`、`hotfix/*` 的分支策略和合并流向。
- 标签默认使用 `vx.x.x` 或 `vx.x.x-alpha.N`、`vx.x.x-beta.N`、`vx.x.x-rc.N`，命名细节见引用文档；已有项目标签约定不自动迁移。
- 发布、出包或测试分发意图默认只做 Git 触发：推荐基线和标签，确认后最多创建并推送发布分支或标签。
- 禁止把发布意图扩展成本机出包、归档、导出、上传、签名或发布平台操作，除非用户明确说“不要走标签，改成本机发布”或等价指令。
- 找不到 CI 或远端工作流配置时，只报告远端监听不可见或需要用户确认监听规则；不得回退到本机构建、归档或上传。
- 分支/标签写操作前必须检查 Git 状态，并确认具体操作和目标仍在用户授权范围内。
- 推送后停止，不跟踪远端构建、上传或发布平台状态。
- 远端失败但缺少具体错误时，只收集失败原因原文，不猜测修复。

## 模式选择

- `branch-policy`：用户询问分支规范、多版本并行、发布/紧急修复/功能分支选择。
- `branch-maintenance`：用户明确要求创建、切换、合并、删除或回流某个分支，或明确确认此前推荐的具体分支操作。
- `recommend-git-trigger`：用户表达发布、出包、测试分发、应用商店发布、内测、公测、正式发布或发布候选意图，但尚未确认 Git 操作。
- `apply-git-trigger`：用户已确认目标基线和标签，要求创建/推送分支或标签。
- `workflow-failure-evidence`：用户反馈分支/标签触发后的远端工作流失败、缺少日志、缺少上传历史或不知道失败原因在哪里看。

发布类请求尚未满足执行授权与目标条件时进入 `recommend-git-trigger`；条件已满足时直接进入 `apply-git-trigger`，不重复请求同一授权。两种模式都不展开成平台发布计划。

## 入口授权门禁

1. 先读取当前分支和工作区，只把它们作为事实，不从分支规范推导写操作。
2. 结合最新指令与会话中仍有效的明确授权，确定本轮 Git 操作及目标；补充信息不使原授权自动失效。先前策略讨论、技能规则和风险判断不能补充授权；目标改变、授权被撤回或实际操作超出范围时重新澄清。
3. 如果没有明确的分支生命周期操作，保持当前分支，不进入 `branch-maintenance`。用户只要求提交时，交给普通 Git 提交流程在当前分支完成。
4. 如果用户只询问策略，进入 `branch-policy` 或 `recommend-git-trigger`，只输出建议；推荐分支不等于获准创建或切换。
5. 只有分支操作及目标明确时才进入 `branch-maintenance`；目标不明确或实际操作超出确认范围时停止并澄清。

## 操作协议

### 分支规范或维护

- 按引用文档的“分支策略”和“合并策略”输出建议。
- 执行前复述本轮获准的分支操作和目标；若用户没有显式授权分支变更，报告保持当前分支并停止分支维护。
- 涉及发布/紧急修复分支时，必须按引用文档说明冻结范围、必要修复的进入方式、紧急修复分支适用条件及回流计划。

### 推荐标签触发

- 按引用文档的“Git 检查”只读检查 Git 状态、目标引用，以及仓库内版本声明和 CI 配置；命令与信息范围以该清单为准。不得运行构建、测试、归档、上传、签名、平台查询或依赖安装命令。
- 按“标签策略”确定版本阶段与标签，按“基线策略”确定基线，并解析目标提交 SHA；同一发布单元内核对历史，工作区当前 `HEAD` 不代替目标提交。
- 按“工作流触发模式”区分推荐监听方式和实际配置；配置不可见或与建议不符时报告差异，不自动迁移。
- 输出推荐基线、目标提交、标签、实际触发证据或缺口，以及需要授权的 Git 操作，然后停止；已有明确执行授权的任务按模式选择进入 `apply-git-trigger`。

### 执行标签触发

- 按“Git 检查”重新核对当前分支、工作区、远端、目标发布分支/标签和目标提交，确认仍符合已授权方案。
- 如果工作区不干净、标签已存在、缺少版本/标签，或目标基线违反规则，停止并请求确认。
- 只执行已确认的最小 Git 操作：必要时切换/创建基线分支，对已确认的目标提交创建标签，推送相关分支，推送标签；创建标签本身不要求切换分支，各项分支操作仍须单独在授权范围内；不得追加构建、测试、归档、上传、签名、平台查询或远端状态追踪。
- 推送完成后只报告 Git 结果和配置证据支持的远端触发预期；手动触发流程仅说明对应标签输入，不自动启动。未见配置时明确未知，不声称已出包或发布成功。

### 收集失败原因

- 按通用触发约定的“失败证据”收集触发信息、运行信息和错误原文；涉及 Apple 时按平台引用文档的优先检查顺序和最小信息清单补充，尤其核对首次上传无历史的情况。
- 拿到失败原因原文后，再交给调试、平台配置或实现修复任务。

## 最终汇报

- 选定模式。
- 推荐或已执行的发布单元、基线分支及目标提交 SHA。
- 推荐或已执行的标签。
- 远端实际触发方式、监听模式或手动输入，以及配置证据或未知项；推荐方案与实际配置不符时列出差异。
- 已执行的 Git 操作；如未执行，说明等待确认或阻塞原因。
- 如涉及失败收集：已建议检查的失败信息入口和仍缺少的失败原因原文。
- 如涉及发布/紧急修复分支：回流和同步计划。
